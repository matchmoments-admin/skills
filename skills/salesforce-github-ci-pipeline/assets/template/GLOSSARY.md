# Domain glossary

The words the pipeline and its code use. Module names in `pipeline/` follow these terms.

| Term | Meaning |
| --- | --- |
| **Story** | One unit of work with acceptance criteria. Lives in the **tracker** (a GitHub issue today, a Jira issue later). Identified by its **story key**: `12` on GitHub, `LIFE-123` on Jira. |
| **Story branch** | The git branch for a story. Its name is the story key in branch form: `issue-12`, or `LIFE-123` for Jira. Nothing else; the title stays on the PR. |
| **Sprint** | A time box with a name such as `2026-w41`. Has a **release branch** `release/<sprint>`, a tracker container (GitHub milestone `Sprint <sprint>` or a Jira sprint) and a **staging org**. Only one sprint is open at a time. |
| **Release candidate** | The open release branch, proposed for production by the **release PR** into `main`. |
| **Hotfix** | A story labelled `hotfix`: its branch starts from `main` and its PR targets `main`. |
| **Tracker** | Where stories and sprints live. One module with two adapters: GitHub Issues and Jira. |
| **Story org** | The scratch org for one story (alias `issue-12`), built from production's **shape** and the story branch. Lives 7 days (`org ensure` rebuilds an expired one); deleted when the story merges. `ORG_RESERVE` (a repository variable) keeps that many slots free for staging, UAT and CI. `org ensure` finishes one that a failed run left half made (its admin user's Title reads `pipeline: ready` only after every step). |
| **Staging org** | The scratch org for one sprint (alias `staging`), holding the whole release branch. Lives 30 days; deleted when the sprint ships. |
| **UI regression** | Every UI spec (`e2e/`) run against the staging org, one browser, to prove a release did not break a screen an earlier story shipped. Once per release by default (`UI_REGRESSION`): it starts when the release PR opens, beside UAT; the release gate needs its status `pipeline/ui-regression` on the head (carried across commits that change nothing staging tests). Story merges in between run Apex and Flow only. |
| **Lane** | One job at a time in an org, and a queue that drops nobody (`pipeline/src/lane.mjs`, `pipe lane acquire|release <org target>`). A git ref `refs/locks/<org lock>` (`org-issue-12`, `org-staging`) created atomically through the API; waiters poll; a holder whose run finished, or older than the TTL, is taken over by a fast-forward-only update (exactly one winner). Every job that deploys to or tests in a story or staging org holds the org's lane: `issue-start`, `ai-implement`, `ai-fix`, `ui-test`, CI and `staging-deploy`. The fix and UI-test jobs **park** instead of polling (`--park <kind>`): a waiter ref `refs/lane-waits/<lock>/<ms>-<kind>-<run>-<job>`, re-run by `lane-wake.yml` when the holder releases (only real, finished, latest-attempt fix and UI-test jobs), and only while still owed (`stillOwed`: the waiter ref points at the PR head it parked on; a person's push since, a closed PR, or a passed or newer UI test drops it); one waiter per kind per lane. The hourly reconcile starts a wake when a parked job waits for a free lane (`pipe lane due`: its holder died before letting go). CI's lane step fails on a busy lane or an API error (`--optional` only skips targets with no org). GitHub's concurrency groups are not used for orgs (they keep only the newest waiting run and cancel the one before it), except the UAT stand-in, where only the newest deploy matters. |
| **Org registry** | How a later job finds an org an earlier job made: the Dev Hub's `ScratchOrgInfo` records, matched on Description (`issue-12`, `staging-2026-w41`). |
| **Shape** | Production's edition, features and settings, captured in the Dev Hub. Scratch orgs copy it; code and data never come from it. |
| **Verdict** | A gate input produced by an agent-free job as a commit status on the exact commit it judged: `pipeline/ai-review` and `pipeline/ui-test`. The AI review's text is written only by `gate.REVIEW` and read only by `gate.reviewKindOf` (passed, changes, not-needed, overruled, budget, running, none): Standing's `review.kind`. Labels such as `review:pass` are for people only. A failed verdict on the code always blocks. |
| **Build plan** | Claude's proposal for a story before it is built (`/plan`): components, tests, risks, size and numbered open questions, as one comment edited in place. People answer in comments; the latest plan and the answers after it are the **agreed plan**, part of the spec every agent reads. Optional: small stories go straight to `/start`. |
| **Action** | Something a person makes the pipeline do: plan, start, build, review, fix, UI test, sign off, UAT pass, check again, re-run CI / staging / UAT (`pipeline/src/actions.mjs`). Two doors, one effect: a **tick box** on the card (offered only when it makes sense) or a comment command. Write access only. A sign-off is the trusted status `pipeline/sign-off`; a UAT pass is `pipeline/uat`; the rest start their workflow. |
| **Release card** | The card on a release PR: what ships, CI, the staging regression, UAT, approval, production validation, merge, production and close-out, with what to do next and the boxes for it. The release workflow and close-out keep it current; it ends "Done" with the tag. |
| **Spec** | An issue (label `spec`, the **New spec** form) for work bigger than one story. Claude writes its spec as one comment (`/spec`); a person answers its questions, then ticks **Make it a story**. The release that ships its last story closes it ("Done: shipped in vX"). |
| **Vendored library** | Third-party source (FFLib and the like) kept unmodified under `force-app/vendor/<library>/`, listed in `docs/vendor.md` (repository, pinned commit, why), added and updated only with `scripts/vendor.sh` (byte for byte upstream at that commit). It deploys and its tests run; the access check, Code Analyzer, Prettier, the context pack and the AI review skip it, since it is not ours to fix. Our code that uses it is checked as usual. |
| **Slack action** | A button on a Slack notice that does what the card's tick box does, as the person who clicked (their Slack user linked to their GitHub login): start the sprint, make the story, rewrite the spec, plan, start, build, fix, re-run CI, review again, UI test, or answer a spec's or plan's questions in Slack. Never an approval (that is the person's own review in GitHub). Optional: the Slack actions Worker and `SLACK_ACTIONS`. |
| **Slack notice** | A message to one Slack channel when a card's turn changes: a person is needed (its **Next** line), something failed, or a release shipped. Optional (the `SLACK_WEBHOOK_URL` secret); never while the pipeline is working, never twice for the same turn. |
| **Make it a story** | The agent-free action on a spec (`/story`; `/tickets` still works): the spec becomes **one** Story issue, its user stories the acceptance criteria, `Part of spec #N` in its body, so every agent on the story reads the whole spec (`pipe tracker story`). Made once: a second tick links the same story. More stories only by hand, with `Blocked by #N` (checked at Start and at merge: merged, not merely started). |
| **Context pack** | The section "The codebase today" at the end of the story file every agent reads (`pipe tracker story --pack`): for each object the story names or the change touches, what already exists (fields, triggers, record-triggered Flows and their run mode, other Flows that read or write it, validation, workflow, sharing and duplicate rules, page layouts, Apex and its sharing keyword, tests, permission sets), in `force-app` and in the **Production baseline** (marked *production*: built outside the pipeline), and production's **org-wide defaults** (internal and external, from `baseline-facts/sharing.json`, which the baseline refresh captures: the agents' jobs never log in to production). The AI review checks the change against it. Capped per section, so it stays small in a large repo. |
| **Access check** | `pipe access check`: a deterministic least-privilege check of what a change adds (`pipeline/src/access.mjs`), run in CI with or without AI. Blockers fail the build: profiles, administrator permissions, View All / Modify All, Apex with no sharing keyword or unexplained `without sharing`, a Flow without sharing, a new field or object no permission set grants, a new permission set no permission set group lists (a `Feature_<Name>` switch excepted). An exception is an entry in `config/access-exceptions.json` (a pipeline path, so a reviewed maintenance change). |
| **Readiness** | Jev's cheap check of a story (`AI_TRIAGE`): is each acceptance criterion testable, is the story large. Posted only when something is weak; suggests `/plan`. |
| **Gate status** | `pipeline/gate`, the gate's own verdict on a PR's current commit. The branch rules require it, so GitHub's merge button stays locked until every requirement is met; a new commit locks it again. |
| **Emergency merge** | A merge by someone on the branch rules' bypass list (admins, and any team lead team named there) without the gate. Logged by GitHub; the `merged` workflow comments who and starts the follow-ups the gate would have. |
| **Code host** | Every GitHub call behind one interface (`pipeline/src/github.mjs`): statuses, check runs, dispatches, runs, the App's GraphQL, the event log's writes, and facts fetched once per process (the open release branch, a release branch's PR `releasePrOf`, a story's PR, a PR's gate facts; `checkRuns(sha, name)`, the one reader of check runs outside the gate's own gather; `forget(pr)` after starting work on it, so its card reads fresh facts). `pipe.mjs` is only a command table over the modules; a Bitbucket or GitLab host would be a second adapter. |
| **Event log** | One JSON file per thing that happened, under `events/` on the `metrics` branch (`pipeline/src/events.mjs`): stage, tests, validation, gate, org, lane, verdict, agent, release, rollback. Written by the `pipe` command that knows the outcome (best effort, never fails it; a payload never names the envelope's own fields, `kind`, `run`, `at`...); read once a week by `metrics` for DORA to production, time per stage, gate waits and AI cost. The tip keeps 180 days (the weekly metrics run, `pipe metrics --prune 180`: one fast-forward commit, history keeps the rest), so a reader's fetch stays the same size however long the pipeline runs. |
| **UI evidence** | The screenshots a passing UI test took with `evidence()` (one per acceptance criterion, small WebP), posted as one comment on the story and linked from the card's UI test row. Behind `UI_EVIDENCE` (off unless `true`). Kept on the `evidence` branch for the latest passing commit of open stories only (`pipeline/src/evidence.mjs`). |
| **Org provisioning** | The one way an org gets ready (`pipe org ready <target>`, `org.mjs` `ready`): find it, or allocate one (`allocate`: a **warm pool** org made ahead from the snapshot when `ORG_POOL` keeps some, else a new org from the snapshot or production's shape, within the Dev Hub's limits and `ORG_RESERVE`), packages, the source in the working directory, prepare, test data, and a marker for the commit it holds, so a second call for the same commit does nothing (CI's test of a commit in the story org moves the marker when its delta provably brought the org there: `pipe org advance`). A job for a PR that is no longer open never rebuilds the story org (`org.createRefusal`); the janitor removes a story org made before its story merged (and a closed, unmerged story PR gives its org back at once), and when no slot is free the error names who holds them. CI's org comes through it too (`pipe org ci`, `org.mjs` `ci`): the live story org attached (a half-made one completed), a gone one rebuilt once, and a temporary org only for a branch with no org of its own or when the story org cannot be made now (no slot past `ORG_RESERVE`, its PR not open), so a push never spends a daily org it need not. |
| **Production baseline** | `baseline/`: production's customisations that `force-app` does not hold (`config/baseline.json`: all of production by default, minus managed packages, the platform's own components and exclusions), captured read-only by `prod-baseline` after each release and weekly into one bot PR. Every scratch org gets it with `force-app` in one deploy; it never ships to production. It includes approval processes and assignment, auto-response and escalation rules (the production users they name become the scratch org's admin), and production's sharing defaults where they differ from a new org's; a component a scratch org cannot hold is left out of that deploy and named, the rest still deploys. Production's managed packages come from `config/packages.json`; one missing there is reported with the drift. |
| **Snapshot** | A scratch org snapshot (`snapshot-refresh`, names `LCB<yymmddhhmm>`): production's shape, packages, the baseline, main and the test data, already deployed. New orgs start from the newest Active one (fallback: shape). A snapshot Salesforce refuses once is tagged `snapshot-refused-<name>` and skipped from then on. Rebuilt after releases and weekly (skipped when the newest is under 20 hours old), and whenever the baseline or seed changes. |
| **Test data (seed)** | `data/seed`: synthetic records (`sf data import tree`, date tokens filled at load time) that org provisioning loads once per org (a marker Account), and a story's own in `data/seed/stories/<key>/`. For people, UI tests and Flow checks; Apex tests never see it. In the snapshot. |
| **Persona** | The user a story is for: a `Persona:` line in its Access section (a role and the persona's **permission set group**, or loose permission sets where no group exists yet). Logins for testers are made as the persona. |
| **Persona group** | A permission set group for one business role or process (`Support_Agent`), listing the capability permission sets that role needs. Users are assigned groups; the access check fails a new permission set no group lists (a `Feature_<Name>` switch excepted: chosen users hold it). _Avoid_: role (that is the sharing hierarchy), profile. |
| **Settings** | The repository variables. Every workflow passes all of them in one line, `PIPELINE_VARS: ${{ toJSON(vars) }}`, and `pipe` reads them (`setting(name)`; an env var of the same name wins), so a new switch needs no workflow edit. |
| **AI feature flag** | A repository variable (`AI_PLAN`, `AI_IMPLEMENT`, `AI_REVIEW`, `AI_FIX`, `AI_UI_TEST`, `AI_AUTO_CHAIN`, `AI_TRIAGE`) that turns one AI step on. Unset = off; with all off the pipeline is manual. Each flag replaces exactly one manual step, and the gate requires an AI verdict only when its flag is on. |
| **Triage** | A cheap typed decision by Jev (TypeSafe), behind `AI_TRIAGE`: review risk, and UI failure kind (flake, test, feature). It never writes, and any failure falls back to what the pipeline does without it. |
| **Gate** | The decision whether a PR may merge, and how. Routes: **feature** (story into the release branch, squash), **hotfix** (into `main`, squash, then release), **release** (release branch into `main`, merge commit, then release), **back-merge** (`main` into the release branch). |
| **Approver** | The person who approves a story (its `### Approver` section; Make it a story fills in the first of `APPROVERS`). With `APPROVERS` set, an approval counts only from the story's approver (or anyone in `APPROVERS` when none is named, or when the approver pushed the latest change), and never from whoever pushed the latest change, except in **solo approval** (`APPROVAL_MODE=solo` with one name in `APPROVERS`: that person's approval of their own push counts once the AI review passed on it or they overruled it, and the approval record says "solo" and which). The rules are `pipeline/src/approval.mjs`: `approvalProblem` (may approve the code) and `authorityProblem` (may approve, overrule the AI review, or extend the AI budget: spending, so any approver); `gate.approvalProblemFor` and `authorityProblemFor` apply them to the facts; the gate, the cards, Sign off, `/review-ok` and `/budget-ok` all use them. Unset: anyone with write access. |
| **Delivery record** | The marked comment close-out writes on each shipped story (`closeout.deliveryRecord`): the named approver, who approved and when, who pushed the latest change, the AI review or who overruled it with the full reason, the UI test and evidence, the UAT signer, the tag and production validation id, and hours per stage (story opened → PR → approved → merged → in production). The approval is the gate's own record (`pipeline/approval` on the merged head, written as it decided to merge), so a later change to `APPROVERS` never rewrites it. A JSON line carries the same fields for GitHub or Jira reports. |
| **Bring my Setup changes** | `story-retrieve`: what people changed by clicking in a story's scratch org (SourceMember rows not changed by the org's own admin user, which every pipeline deploy runs as; never profiles) is retrieved into `force-app` and committed to the story branch as the App, the person as co-author. Pairs with **Send me an admin login**. |
| **Sign-off** | The human input to a gate: an approving review, or (story PRs into the sprint) the **Sign off** box or `/ship`, recorded as the trusted status `pipeline/sign-off`. PRs into `main` need an approving review. A back-merge needs none: it only carries code already approved and in production. |
| **Production validation** | A check-only deploy of the **candidate** to production. A gate input for PRs into `main`; the release quick-deploys it only for the exact tree it checked. |
| **Shipping** | Getting one merge commit into production, keyed by its SHA (`pipeline/src/shipping.mjs`). The gate builds the **candidate** itself (the base's tip now, with the decided head merged) and validates it while it holds the lock on `main`; after merging, the release receives the merge commit's SHA and the validated tree, quick-deploys only if they match and validates again otherwise, tags that SHA, and closes out from it and the **previous release** (the newest `v*` tag it contains). A SHA already inside a release tag is a no-op. The **watchdog** (in `reconcile.yml`, hourly) starts a release for Salesforce changes on `main` that never shipped, unless production was rolled back. |
| **Close-out** | What the release does after deploying: close shipped stories, carry over unfinished ones, close the sprint, delete its orgs and branch. |
| **Standing** | What still counts on a PR's head (`gate.standing(facts)`): each verdict, the approval under the route's rule, each required check. The only reader of the pipeline's results: no other module or workflow reads `pipeline/*` statuses (a test enforces it; `pipe gate standing --pr N --result uat` answers a workflow, `gate.statusOn` one exact commit). Each result has a **phase**: owed, running, passed or failed. It decides trust (statuses by the pipeline only), carry-over (`gate.RESULTS`, one row per result with its inputs: a review or sign-off survives a spec-only push; CI's Salesforce tests survive any push that changes nothing under force-app; the UI test, UAT and the gate's approval record need the exact head; a diverged history carries nothing; the newest commit's result first, so an older commit's run that finished late never hides a newer one's) and who may approve. The gate, the cards, the board and the **Delivery record** all read it, so they cannot disagree. |
| **Simulated code host** | An in-memory GitHub for tests (`pipeline/test/sim.mjs`): commits, statuses, check runs, reviews, comments, runs and dispatches behind the same `io` seam `codeHost` takes, so the real `gather`, gate, journey, cards and actions run on one world. Scenarios replay journeys on it and check the invariants after each step (`invariants.mjs`); it found two bugs no unit test had (a running review read as "run it again"; an older commit's late result hiding the newer one's). |
| **Harness overlay** | Main's rules and test harness laid over a branch's checkout, hidden from git (`pipe harness overlay <role>`, `pipeline/src/harness.mjs`): implement and fix get main's `CLAUDE.md`, `REVIEW.md` and `docs/agents`; the UI test adds `e2e/support`; staging gets `e2e/support`. Run after the branch is checked out and up to date. Nothing an agent commits carries main's copy back. |
| **Start decision** | Whether a job needs a runner at all, decided in main's code before it starts (`pipeline/src/start.mjs`): `pipe start review|fix|ui-test` for the AI steps and the UI test (dispatch, or post the verdict or the reason), `pipe ci plan` for CI (branch kind, the org it tests in, whether anything needs an org or a UI test), `pipe start followups` for what starts after a merge. A verdict that still stands on the head (Standing) is not run again unless a person asks (a label or ticked box). A story over its **AI budget** gets no runner at all (`start.stopForBudget`: comment, `blocked`, card); `ai-implement`, which a label starts, checks it before the org's lane (`pipe agent stop`). |
| **Journey** | The order a change travels in and what starts next when a stage finishes (`pipeline/src/journey.mjs`, `pipe next --after review|ci|staging|release-pr|org-freed`): after a review, a fix or Claude's UI test (the UI test only once CI's org job passed on the head; CI's finish starts it otherwise, so no runner waits for the story org); after the staging regression, the release PR opening or an org slot freeing up, UAT. Decided from the head's **Standing**, so a stage is started only when its result is owed. |
| **Finish** | The last step of every job that produces a result (`pipe finish review|ui-test|ci|staging|uat`, `pipeline/src/finish.mjs`): the verdict on the commit it judged and the label people read, the gate if a person already acted, the card, then what the journey owes, always in that order. The verdict's text per outcome is one table (`verdictOf`), not bash in each workflow. |
| **Reconcile** | The sweep (`pipe reconcile`, in `reconcile.yml` every hour, with no Salesforce key): runs GitHub never started (billing) re-run once; then on every open story and release PR that nothing is running for, the gate re-run if an approval waits on a stale gate status (never a gate production rejected on that head), and whatever the journey owes on its head (`next --after any`), started. Level-triggered, so a dropped `workflow_run` costs one tick, not a stalled story; idempotent, since what it started is running at the next tick. |
| **Pipeline improvement** | A ticket about the pipeline itself, opened by a failed pipeline run (`improve.yml`, `pipeline/src/improve.mjs`) or by a person. A failure that is the story's own opens none. One ticket per failure **signature** (workflow, job, step, error without ids or times): a repeat adds "seen again". Fixed by a maintenance PR that closes it. _Avoid_: bug, incident. |
| **Agent role** | One AI job (implement, fix, review, ui-test, plan, spec): its model and turn budget from the **Model policy** (`pipe agent budget`), its output format in `verdict.mjs`, its rules in `docs/agents/`. |
| **Model policy** | `config/ai-models.json`, read by `pipeline/src/roles.mjs`: the default provider and model, each **provider** (`anthropic` subscription token, `anthropic-api` key, `bedrock` and `vertex` through GitHub's OIDC identity, an Anthropic-compatible `gateway`) with its model id per alias (`sonnet`, `haiku`, `opus`), each role's model and turns, a review's cheaper model for a change with no code, access or automation, and **experiments** (a share of stories, by a stable hash of the key, on another model: its **arm**). `AI_MODEL_<ROLE>` and `AI_MODEL` override it for a trial. Only review and plan may run a model that is not Claude. Each agent event records provider, model and arm, and the weekly metrics compare them (cost, failed runs, reviews overruled). A story's agents stop at its **AI budget** (`AI_STORY_BUDGET_USD`, from the agents' own cost reports); an approver's `/budget-ok <why>` adds as much again. |
| **Review eval** | The reviewer eval set: changes with a known defect, or none, in `config/review-evals/<case>/` (story, diff, expected verdict and what the review must name). `review-eval.yml` has a model review each one as `ai-review` would; `pipeline/src/review-eval.mjs` scores defects caught and false alarms, recorded as an `eval` event and shown per model in the weekly metrics. How a cheaper model or an experiment arm is judged on quality, not only cost. |
| **Branch kind** | story, release, backmerge or maintenance (`start.branchKind`): the one rule every workflow reads (CI's job outputs carry it). |
| **Pipeline identity** | The GitHub App the pipeline acts as, so its PRs and pushes trigger CI like a person's. |
